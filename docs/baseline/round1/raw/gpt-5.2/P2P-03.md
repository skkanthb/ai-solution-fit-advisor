## Prompt

```
I'm an enterprise architect scoping an AI solution for this ERP / supply chain use case:

Three-way match exception resolution: Invoices that fail PO / goods receipt / invoice matching sit blocked while AP chases buyers and receivers.

What AI approach and models would you recommend?
```

## Answer

For three-way match exception resolution, the most effective pattern is **a decision-and-routing system built around LLM-assisted case triage + evidence retrieval**, paired with **targeted ML models** for prediction and anomaly detection. Don’t try to “let an LLM decide payment”—use it to **explain, gather missing info, propose resolution actions, and automate comms**, while deterministic rules + workflow controls enforce policy.

Below is a practical enterprise architecture recommendation.

---

## 1) Recommended AI approach (end-to-end)

### A. Case triage + root-cause classification (ML + rules)
Goal: classify why the invoice failed match and what to do next.

**Outputs**
- Exception category (price variance, qty variance, missing GR, PO closed, wrong supplier, tax/freight mismatch, unit of measure, duplicate invoice, partial receipt, service entry missing, etc.)
- Severity / risk score
- Suggested next action: auto-clear, auto-route to buyer, route to receiving, route to vendor, request credit memo, create PO change request, create GR, etc.

**How**
- Start with deterministic checks (tolerances, known config, vendor terms).
- Add a supervised classifier to improve accuracy and reduce brittle rule sprawl.

**Models**
- Gradient boosting (XGBoost/LightGBM/CatBoost) for structured ERP features
- Optionally a multiclass deep model if you have huge volumes, but tree-based usually wins in ERP tabular data.

---

### B. “Evidence assembly” via retrieval (RAG) + LLM reasoning
Goal: for each blocked invoice, automatically compile a **human-ready packet**: what happened, what’s missing, and the most likely fix.

**Retrieve**
- PO header/items, PO change history, approvals
- GR / service entry sheets
- Contract/pricing conditions, info records
- Email threads / notes / ticket history (if available)
- Vendor master, payment terms, historical exception patterns
- Policies: tolerance rules, delegation of authority, SOX controls

**RAG approach**
- Index unstructured documents (contracts, emails, PDFs) and semi-structured notes.
- Retrieve with hybrid search (BM25 + embeddings).
- Provide retrieved citations to the LLM to ground responses.

**Models**
- Embedding model: OpenAI `text-embedding-3-large` or similar enterprise-grade embedding (or on-prem like bge-large).
- Reranker: Cohere Rerank / bge-reranker / LLM-based rerank.
- LLM: GPT-4.1 / Claude 3.5 / Gemini 1.5 Pro, or on-prem (Llama 3.1 70B / Mixtral) depending on data residency.

---

### C. Recommended-action generation (LLM + constrained tools)
Goal: propose a resolution plan and execute safe steps via tools.

**Pattern**
- LLM as an “agent” that can call tools:
  - Query ERP for missing data
  - Open/append a case
  - Draft message to buyer/receiver/vendor
  - Populate a PO change request draft
  - Draft a GR request / service entry reminder
- Hard guardrails:
  - LLM cannot post financial documents directly unless explicitly approved
  - Enforce policy and segregation of duties in the workflow engine
  - Every recommendation includes: confidence, rationale, citations, and required approvals

**Best practice**
- Use structured function calling with strict schemas for outputs (JSON), not free-form.

---

### D. Prediction models to reduce cycle time (ML)
These are high-leverage and typically ROI-positive:

1) **“Time-to-resolution” and “next best owner” prediction**
- Predict who will resolve fastest (buyer vs receiver vs vendor)
- Predict SLA breach risk → escalate early

2) **Auto-clear eligibility model**
- Predict probability an exception is benign and within tolerance (with strict policy)
- Gate with deterministic compliance rules

3) **Duplicate / fraud / anomaly scoring**
- Unsupervised or semi-supervised: Isolation Forest / autoencoders
- Supervised where labels exist: GBM classifier
- This is crucial if you increase auto-resolution—you need risk controls.

---

## 2) Model recommendations by component

### Structured/tabular ML (high accuracy, explainable)
- **LightGBM / XGBoost** for:
  - exception category classification
  - SLA risk
  - auto-clear propensity
- Pros: fast, strong on ERP data, SHAP explainability.

### LLM for language + reasoning over retrieved context
Pick based on constraints:

**Cloud (fastest to deploy)**
- **GPT-4.1** (or similar top-tier) for best reasoning and tool-use reliability
- Use smaller model (GPT-4.1-mini / GPT-4o-mini class) for:
  - drafting emails
  - summarization
  - classification if cost-sensitive

**On-prem / VPC**
- **Llama 3.1 70B** (or 8B/70B mix) with RAG
- **Mixtral 8x22B** for strong throughput
- Note: tool-use reliability and instruction following typically stronger with frontier hosted models; you compensate with more engineering/validation on open models.

### Embeddings / retrieval
- OpenAI `text-embedding-3-large` (strong general performance)
- If on-prem: **bge-large-en**, **e5-large**, and a reranker model (often boosts relevance more than “better embeddings” alone).

---

## 3) Data/features that matter most

### Core structured features (from ERP)
- PO price vs invoice price deltas (absolute and %)
- Quantity received vs invoiced; partial receipts
- GR posting dates vs invoice dates (timing issues)
- Tolerance keys and thresholds (by vendor/material/plant/company code)
- PO change history after GR (common root cause)
- Vendor performance: historical exception rate, avg resolution time
- Buyer/receiver workload + latency patterns (for routing)
- Material/service type, UoM conversions, tax/freight conditions
- Duplicate indicators (invoice number similarity, amount patterns)

### Unstructured sources (high value for RAG)
- Contract clauses, special pricing agreements
- Email chains about delivery discrepancies
- Receiving notes, quality holds, ASN/packing slip scans
- Prior case notes (“this vendor always invoices freight separately…”)

---

## 4) Workflow design (where AI provides real value)

### Typical automated path
1. Detect exception + assemble evidence packet
2. Classify root cause + confidence
3. If “low risk + within tolerance + policy allows” → recommend auto-clear (or auto-clear with audit trail)
4. Else route to the correct owner with:
   - concise summary
   - missing info checklist
   - proposed fix steps
   - pre-drafted message to counterparty
5. Track responses; auto-remind/escalate; update case notes automatically

### Human-in-the-loop controls (SOX-friendly)
- Approval gates for:
  - posting changes (PO, GR, invoice)
  - tolerance overrides
  - vendor master changes
- Full audit log: what data the model saw + citations + who approved

---

## 5) Build vs buy guidance
If you’re evaluating platforms:
- AP automation suites often handle OCR + basic matching, but **exception resolution** is where a custom layer wins because it depends on your policies, plants, buyer behaviors, and contract corpus.
- A hybrid is common: buy invoice capture / workflow, build the **exception intelligence layer** (triage + RAG + routing + comms).

---

## 6) Suggested implementation phases

1) **Phase 1 (6–10 weeks): Triage copilot**
- RAG + LLM to generate case summaries and draft outreach
- No auto-posting; measure time saved and response latency

2) **Phase 2: Root-cause classifier + smart routing**
- Train LightGBM on historical exceptions + resolutions
- Add SLA risk scoring and escalation logic

3) **Phase 3: Safe automation**
- Auto-clear for narrow scenarios (e.g., freight/tax variance under threshold, known vendors)
- Introduce anomaly scoring and stronger controls

---

## 7) What I would recommend as a default “reference stack”
- **Workflow/case**: ServiceNow / SAP Build Process Automation / Power Automate (depending on your ERP and IT standards)
- **Feature store / ML**: Python + LightGBM; SHAP for explainability
- **RAG**: vector DB (Pinecone/Weaviate/Azure AI Search/OpenSearch) + reranker
- **LLM**: GPT-4.1-class for agent/tool orchestration; smaller model for bulk drafting
- **Guardrails**: strict function schemas, allowlisted tool actions, policy engine, audit logging
